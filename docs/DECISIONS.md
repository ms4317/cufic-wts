## 2026-07-17 · 뉴스 → 등급제 힌트, 강사가 조별 차등 지급

`news`(전체 공개)를 `hints`(S/A/B/C/D 등급)로 바꾸고 `hint_grants`로 조별 지급을 기록한다.
**조마다 보이는 힌트가 다르다** — 이게 기존 `is_published` 방식과 결정적으로 다른 점.

- **왜** — 하위권 우대·랜덤·재량을 섞어 배분한다. 배분 판단은 사람이 하고 시스템은 기록만 한다.
- **격리 방식** — `hints`·`hint_grants`에 select 정책을 만들지 않아 REST로 통째로 긁을 수 없다.
  지급받은 힌트는 `get_my_hints(팀코드)` RPC로만 나온다.
  - **왜 RLS 정책이 아니라 RPC인가** — 인증이 없다(anon key + 참가 코드). RLS가 "자기 조"를
    알 방법이 없다. RPC로 코드를 받아 거르는 게 같은 결과를 내면서 확실하다.
  - **대가** — Realtime은 RLS를 쓰므로 힌트 지급을 실시간 구독할 수 없다. §5에서 폴링이나
    별도 채널로 풀어야 한다. 진짜로 필요해지면 Supabase Auth(JWT에 team claim)로 가야 한다.
- **부수 결정** — 힌트 등급은 시드에서 "예고하는 등락폭 크기"로 자동 부여한다(S=50%↑).
  더미 데이터라도 앞뒤가 맞아야 관리자 화면 테스트가 의미 있다.

## 2026-07-17 · 즉시 체결 → 주문서 일괄 체결

`place_order`(즉시 체결)를 폐기하고 `order_sheets` + `save_order_sheet`로 바꿨다.
조는 라운드 중 종목별 매수량/매도량을 쓰고 언제든 고친다. 관리자가 라운드를 넘기면
전 조 주문서가 **그 라운드 가격**으로 일괄 체결된 뒤 다음 연도 가격이 공개된다.

- **왜** — 작년 게임 규칙 계승. 라운드제와 정합한다 — 라운드 안에서는 가격이 안 변하는데
  즉시 체결은 "먼저 누른 사람이 유리"를 만들지 않지만, 판단을 되돌릴 수 없게 만든다.
  주문서는 라운드 내내 고민하고 고칠 수 있어 교육적으로도 낫다.
- **체결 순서** — 한 주문서 안에서 **매도 먼저 → 매수**. 매도 대금을 매수 자금으로
  인정하는 규칙과 일관되게.
- **⚠ 잠정 규칙 (팀 확인 중)** — 자금 검증은
  `예수금 − Σ(매수×현재가) + Σ(매도×현재가) ≥ 0`. 같은 주문서의 매도 대금을 매수에 쓸 수 있다
  (작년 시트 수식). 바뀔 수 있어 `order_funds_ok()` 함수 한 줄로 분리해뒀다.
- **부수 효과** — 리더보드 실시간 갱신 개념이 사라진다. 정산 시점에만 순위가 바뀐다.

## 2026-07-17 · 참가 코드 비공개 (teams 직접 조회 차단)

`teams`의 읽기 정책을 없애고 `public_teams` 뷰(code 제외)만 열었다. 코드 확인은 `login_team` RPC로.

- **왜** — 힌트를 조별로 격리해도 코드 목록이 공개면 `get_my_hints(남의 코드)`로 다 뚫린다.
  코드가 유일한 신원 수단인 구조에서 코드 공개는 신원 전체를 공개하는 것과 같다.
- **남는 한계** — 코드를 아는 사람은 그 조로 로그인할 수 있다. 코드 기반 인증의 본질이라
  여기서 더 막을 수 없다.

## 2026-07-17 · 백엔드는 Supabase (Postgres + Realtime + RPC)

- **왜** — 필요한 게 전부 한 곳에 있다. 조별 상태 저장(Postgres), 강사가 라운드를 넘기면 모든 조에
  즉시 반영(Realtime), 주문 검증을 서버가 최종 판정(RPC).
- **결정적 이유** — 요구사항의 절반(조별 순위, 전체 조 현황, 모든 조 연동, 관리자 설정)이
  **서버 없이는 원리적으로 불가능**했다. 프론트만으로는 각 브라우저가 독립된 섬이다.

## 2026-07-17 · 주문 검증의 최종 판정은 서버, 낙관적 업데이트 금지

- **왜** — 프론트 검증만 있으면 학생이 개발자도구로 우회할 수 있다. 교육용이라도 성적이 걸리면
  누군가는 시도한다.
- **대가** — 주문마다 서버 왕복이 생긴다. 교실 네트워크에선 체감되지 않을 것으로 보고 감수한다.
  대신 이중 클릭 방지와 실패 토스트로 지연을 드러낸다.

## 2026-07-17 · localStorage 저장 계층을 만들지 않음

새로고침하면 보유·예수금·체결내역이 날아가는 문제가 오래 있었다. 여러 번 저장을 제안했으나
**서버가 곧 대체하므로 만들지 않기로** 했다.

- **왜** — 서버가 붙으면 저장 계층 대부분이 서버 상태로 대체된다. 지금 만들면 두 번 만드는 셈.
- **대가** — 서버 연동 전까지 데모는 새로고침에 초기화된다. 그전엔 실제 수업에 못 쓴다.
- **해소** — §3 재접속 복원(팀 코드로 자동 재로그인 + 초기 로드)이 이 문제의 최종 해결이다.

## 2026-07-17 · 가상 종목 데이터 이식은 서버 뒤로 미룸

지금 데이터는 실제 종목명(삼성전자 등)에 실제에 근사한 주가·재무를 쓰지만 **어디서도 받아오지 않았고
검증되지 않았다.** 전부 기억에서 적은 값이다.

- **왜 미뤘나** — 관리자가 종목명·주가를 편집하게 될 예정이라, 시드 스크립트만 갈면 된다.
  종목명 방식(완전 창작 / 패러디 / 기호명)도 아직 미정.
- **위험** — 그전까지 학생이 "삼성전자 2024년 ROE 8.6%"를 사실로 배운다. **실제 수업 전 반드시 교체.**
- **관련 실수** — LG에너지솔루션 2021년 주가 505,000원은 존재할 수 없는 값이었다(2022년 1월 상장).
  형식을 맞추려고 지어낸 숫자였다. 값을 비워 보합으로 처리하도록 고쳤다.

## 2026-07-17 · 시나리오형 데이터 — 뉴스가 다음 라운드 주가를 예고

뉴스는 "그 라운드에 발표되어 **다음** 라운드 주가를 예고"하는 힌트다. R1의 호재를 읽고 사면 R2에 오른다.

- **왜** — 이게 교육 콘텐츠의 핵심 루프다. 재무제표·뉴스로 판단 → 매수 → 라운드 진행 →
  주가 변동 → 손익 확인 → 뉴스로 복기. 이 고리가 없으면 학생이 뭘 해도 손익이 0이었다.
- **계약** — impact 태그는 다음 해 실제 등락과 **반드시** 일치해야 한다. 어긋나면 정직하게 판단한
  학생이 손해를 본다. `src/data.test.js`가 전수 대조로 이를 고정한다.
- **부수 효과** — 라운드가 연도에 매핑되므로(R1→2022) 재무제표의 미래 연도를 가리는
  스포일러 차단이 자연스럽게 성립한다.

## 2026-07-17 · 평가금액·총손익을 보유종목에서 파생 계산

한동안 `equity`가 고정 상수여서 `cash + Σ(보유×현재가)`와 맞지 않았다(10,482,300 vs 9,459,000).

- **왜** — 주문이 체결되면 잔고가 변하는데 상수를 두면 헤더와 MY 모달이 어긋난다.
- **규칙** — 평가금액 = 예수금 + Σ(보유수량 × 현재가), 총손익 = 평가금액 − 원금.
  `data.js` 상단에 등식을 주석으로 못박았고 `src/actions.test.js`가 체결내역 역산으로 검증한다.

## 2026-07-17 · 원금 1억, 시작은 완전 초기 상태

- **왜** — 학생 시작점. 거래 없음 → 예수금 = 원금, 보유 없음, 손익 0. 정합성이 자명해진다.
- **대가** — 수량이 세 자리가 된다(삼성전자 1,347주). 그래서 10%/25%/50%/최대 비율 버튼을 넣었다.
  스테퍼 −/+로는 감당이 안 된다.
- **최종적으로는** 관리자가 조별로 시드를 설정한다. 1억은 기본값일 뿐 하드코딩하지 않는다.

## 2026-07-17 · 종목 전환 시 주문 수량 0으로 리셋
